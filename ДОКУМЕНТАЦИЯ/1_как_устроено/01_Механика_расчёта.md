# 1. ЧТО ЭТО ЗА ПРОДУКТ

**Счётикс** — калькулятор юнит-экономики для соло-специалиста творческой профессии
(текущая ниша — фотограф). Он отвечает на один вопрос:

> Какую цену за час съёмки надо назначить клиенту, чтобы за год получить на руки
> желаемый доход — после всех расходов, амортизации, налогов, взносов и комиссий?

Ключевая идея, вокруг которой построен весь продукт: **клиент оплачивает только часы
на площадке**, а работать приходится в 7–8 раз больше. Из 1752 часов рабочего года
продаётся ~217 (12 %). Поэтому «наивная» ставка (доход ÷ часы съёмки) занижена в разы,
и весь расчёт — это способ показать реальную цену.

### Воронка

| Шаг | Файл | Что происходит |
|---|---|---|
| 1 | `index.html` | Лендинг: знак, три пользы, кнопка «Перейти к расчёту». Запоминает реферальную метку `?ref=…`. Кто уже был (`localStorage.phc_seen`) — редиректится сразу в анкету, если нет `?hello=1`. |
| 2 | `calc.html` | Анкета из 4 секций (~25 вопросов + 8 таблиц расходов). Живой пересчёт на каждое изменение. Кнопка «Рассчитать» → 7-секундная анимация → переход в отчёт. |
| 3 | `report.html` | Отчёт: 24 элемента в `.wp`, из них 8 содержательных карточек + шапка + справочник + полная таблица. Печать в PDF. |

Бэкенда нет вообще. Весь расчёт клиентский, данные передаются через `localStorage`
(запасной путь — base64 в адресе). Никакие данные никуда не уходят.

### 3.6 `05_Расчёт` (25 строк × 7 колонок) — сердце книги
Колонки B…H: НПД 5 %, НПД 4 %, НПД 6 %, УСН 6 %, УСН 15 %, АУСН 8 %, АУСН 20 %.
Обозначения: `N` = target_income, `C` = total_costs, `a` = acquiring, `sdiv` = site_divisor,
`D = 1 − a − sdiv`, `FIX` = 57 390, `CRED` = 3 000, `CAP` = 321 818.

| Стр. | Показатель | Формула |
|---|---|---|
| 4 | **ВЫРУЧКА R** | НПД: `(N+C)/(D − ставка)` · УСН6: `MAX((N+C+FIX−CRED)/(D−0,01); (N+C)/(D−0,06))` · УСН15: `(TB + FIX−CRED + 0,01·TB + C)/D`, где `TB = N/0,85` · АУСН8: `(N+C+injury)/(D−0,08)` · АУСН20: `(TB2 + C + injury)/D`, `TB2 = N/0,8` |
| 5 | Выручка в месяц | `R/12` |
| 7 | Эквайринг | `R × acquiring` |
| 8 | Фиксированные взносы | УСН: `FIX`; НПД и АУСН: 0 |

Чем длиннее съёмка, тем меньшую долю занимает фиксированный час на клиента — отсюда
законная скидка **без потери дохода**: годовая выручка при любом S одинакова и равна R.

### 3.23 `13b_Программа_лояльности` (55 строк)
Резерв `discP` (5 / 10 / 15 %) закладывается в цену делением: `цена = база/(1−discP)`,
бюджет фонда = `R × discP`. Фонд расходуется по трём направлениям:
1. **постоянным клиентам** — ступени 5 % (раз в полгода), 7 % (раз в квартал), 10 % (раз в месяц);
2. **специальные предложения** — комплект сертификатов (7 × 5 000 + 1 × 10 000 + 23 × 3 000);
3. **скидка за объём** — остаток фонда.
Формулы сходимости: сумма трёх направлений = бюджет фонда (проверка `C21−C17 = 0`).
Принципиальное решение 09.08.2026: экономия на привлечении постоянных клиентов
**не засчитывается** в покрытие скидок — это отдельная выгода фотографа.

# 4. МАТЕМАТИЧЕСКАЯ МОДЕЛЬ

Единая модель, одинаковая в книге и в JS (различия — в разделе 10). Все числа ниже
посчитаны на дефолтных значениях **формы** (доход 110 216 ₽/мес, S = 1 ч, K = 3, cl = 1 ч,
резервы выключены, НПД 5 %).

### 4.1 Время
```
ND = 247 − 20 − 8 = 219 дней
NT = 219 × 7      = 1533 ч            чистое продуктивное время
idle = 219 × (8−7) = 219 ч            рабочие паузы

promo = 2 × 219 = 438 ч
accT  = 3 × 4   = 12 ч                (0, если нанят бухгалтер)
side  = 450 ч
gross = 1533 − 450 = 1083 ч
fmT   = gross × fm_pct, если включён резерв (по умолчанию 0)
pool  = gross − fmT = 1083 ч          ← фонд проектных часов
```
Три равенства, которые обязаны выполняться всегда (проверено численно — выполняются):
```
side + fmT + pool = NT                450 + 0 + 1083 = 1533 ✓
core + clT       = pool               866,4 + 216,6 = 1083 ✓
sh + post        = core               216,6 + 649,8 = 866,4 ✓
```

### 4.2 Проект
```
pt = S×(1+K) + cl = 1×4 + 1 = 5 ч на заказ
py = pool / pt    = 216,6 заказа в год
sh = py × S       = 216,6 ч съёмки в год   ← ЗНАМЕНАТЕЛЬ
post = sh × K = 649,8 ч · core = 866,4 ч · clT = py × cl = 216,6 ч
```
Оплачивается 216,6 ч из 1752 ч рабочего года = **12,4 %**.

### 4.4 Обратная раскрутка выручки
Проценты, которые считаются **от оборота**, идут в знаменатель:
```
a     = (acq_rate/100) × (acq_share/100) + сумма доп. банковских процентов
sdiv  = site_hours / (site_life × NT)          если сайт делали сами
fundP = fund_pct/100    если включён фонд развития
discP = disc_pct/100    если включён запас на скидку
D = 1 − a − sdiv − fundP − discP               по умолчанию 0,973
```
Формулы выручки по режимам (`Ny` = целевой доход за год):
```
без налогов  R = (Ny+C)/D
НПД          R = (Ny+C)/(D − ставка)
УСН 6 %      R = max( (Ny+C+FIX−CRED)/(D−0,01), (Ny+C)/(D−0,06) )
УСН 15 %     TB  = Ny/0,85;  R = (TB + FIX−CRED + 0,01·TB + C)/D
АУСН 8 %     R = (Ny+C)/(D−0,08)
АУСН 20 %    TB2 = Ny/0,80;  R = (TB2 + C)/D
```

## 6.4 `calc()` по шагам

```js
1. promo = EXC.FormPromoTime ? 0 : promo_per_day × 219
   accT  = (acc_mode==='self' && !EXC.Form011) ? acc_per_quarter × 4 : 0
   idle  = 219 × (8−7) = 219
   side  = promo + accT ;  gross = 1533 − side
   fmT   = fm_on ? gross × fm_pct/100 : 0 ;  pool = gross − fmT

2. K = post_ratio ; cl = EXC.FormClientTime ? 0 : client_time ; M = 1+K
   S = shoot_manual ;  pt = S×M + cl ;  py = pool/pt ;  sh = py×S
   post = sh×K ; core = sh+post ; clT = py×cl
   sAuto = (pool/NW − cl)/M            справочная «какая съёмка влезет»

3. wsShare = cab_area/home_area
   wsY = дом ? (home_rent+home_util) × wsShare × 12 : (office_rent+office_util) × 12

4. eduSum, eduMon — из таблицы Form006 (цена курса и месяцы без дохода)
   eduOpp = eduMon × income_month ;  eduY = (eduSum + eduOpp)/edu_life

5. siteY = (исключён || делал сам) ? 0 : site_cost/site_life
   sdiv  = (делал сам) ? site_hours/(site_life × NT) : 0

6. equip = Form001+Form002+Form004
   amort = equip + Form013 + eduY + siteY
   accM  = нанят бухгалтер ? acc_cost_month × 12 : 0
   vari  = Form003 + Form010 + Form007 + accM + wsY
   C  = amort + vari ;  Ny = income_month × 12

7. a = EXC.Form015b ? 0 : (acq_rate/100 × acq_share/100) + сумма доп. комиссий/100
   fundP = fund_on ? fund_pct/100 : 0 ; discP = disc_on ? disc_pct/100 : 0

8. rg = regime; если 'npd' → npd4 / npd5 / npd6 по npd_who
   RT = ставка режима; если tax_off → RT = 0
   D = 1 − a − sdiv − fundP − discP

9. R_ по формулам раздела 4.4

10. taxOf(Rx) — налог от произвольной выручки (17.08.2026):
    НПД     Rx × RT
    УСН6    в = FIX + min(max(0,Rx−300k)×1 %, CAP);  max(0, Rx×6 % − в) + в
    УСН15   б = Rx×(1−a) − C − в, где в = FIX + min(max(0,б−300k)×1 %, CAP)
            (взносы уменьшают базу, а сами зависят от неё → 12 проходов)
            налог = max(б×15 %, Rx×1 %) + в
    АУСН8   Rx × 8 %
    АУСН20  б = max(Rx×(1−a) − C, 0);  max(б×20 %, Rx×3 %)   ← взносов нет

    БЫЛО до 17.08: база для УСН 15 и АУСН 20 бралась от целевого дохода
    (Ny/(1−ставка)) и почти не зависела от Rx. Из-за этого не сходилась
    безубыточность и не работал автоподбор.

11. Выручку и точку безубыточности ищем делением пополам — у налога
    есть изломы (минимальный налог, потолок допвзноса), одной формулой
    их не описать. 90 итераций, точность до копейки:

    выручкаПод(цель): найти R, при котором R×D − C − taxOf(R) = цель
    R_  = выручкаПод(Ny)      если sh > 0, иначе 0
    Rb  = выручкаПод(0)       точка безубыточности
    taxAll = taxOf(R_) ;  aq = R_ × a
    Rc = current_rate × sh ;  leftC = max(0, Rc − C − Rc×a − taxOf(Rc))

    Ограничители (17.08.2026): a ≤ 10 %, fundP ≤ 20 %, discP ≤ 15 %,
    D ≥ 0,40; не-съёмочное время ≤ 80 % рабочего года.

12. возврат объекта d из ~45 полей (раздел 9)
```

## 6.5 Автоподбор и контроль лимитов

```js
ЛИМИТЫ = { npd*: [2 400 000, 'НПД'], usn6/usn15: [20 000 000, 'УСН без НДС'],
           ausn8/ausn20: [60 000 000, 'АУСН'] }
```
`подобрать()` (работает только при включённом `tax_auto`) перебирает `npd, usn6, usn15,
ausn8, ausn20`, для каждого вызывает `calc()`, отбрасывает превысившие лимит и выбирает
**минимум по требуемой выручке `R`**: чем меньше надо заработать ради того же дохода
на руки, тем выгоднее режим.

БЫЛО до 17.08: сравнение шло по «нетто = R − C − taxAll − aq». Эта величина по
построению всегда равна `Ny`, числа получались одинаковыми, и режим выбирался
ошибкой округления — при доходе 60 тыс./мес побеждал худший вариант, УСН 15 %.

`лимит()` вызывает `подобрать()`, затем: если выбран НПД и расчётная выручка выше
2,4 млн — **автоматически** переключает на УСН 6 %, поднимает флаги `ПЕРЕКЛЮЧЕНО`,
прячет пункт НПД в списке, пока выручка не вернётся в лимит; при возврате — снова
включает НПД. `полоса()` рисует уведомление (жёлтое при автосмене, зелёное при возврате),
держит 12 секунд, не перезапускает таймер при повторных пересчётах и прокрутке,
даёт закрыть крестиком.

## 7.5 Собственная налоговая математика отчёта

Отчёт **не доверяет** `Rb`, `leftC`, `taxC` из анкеты и считает их заново:
```js
TX0 = {FIX:57390, THR:300000, CAP:321818, AQ:0.028, INJ:0}
налог0(V, код):
   НПД      V × ставка
   УСН6     доп = min(max(0,V−300k)×1 %, CAP);  max(V×6 % − (FIX+доп), 0) + FIX + доп
   УСН15    база = max(V − costY − V×AQ, 0);    max(база×15 %, V×1 %) + FIX + доп(база)
   АУСН8    V × 8 %
   АУСН20   база = max(V − costY − V×AQ, 0);    max(база×20 %, V×3 %)
нетто0(V) = V − costY − V×AQ − налог0(V)
Vb = решение нетто0(V) = 0 делением пополам, 90 итераций
```
Здесь база «доходы минус расходы» вычисляется **правильно** — от самой выручки.
Таблица режимов (`netNPD`, `netUSND`, `netUSNDR`, `netAUSND`, `netAUSNDR`) использует ту же
логику, а лимиты в ней разведены корректно: `LIM_USN = 490 500 000` (450 млн × дефлятор
1,090), `VAT = 20 000 000` — то есть 20 млн это порог НДС, а не потеря режима.

# 8. СБОРКА И СТОРОЖА

## 8.1 `собрать.py`

Идея: `report.html` — производный файл. Правки идут в `части/каркас.html`, а вынесенные
блоки живут отдельными файлами и подставляются на место меток `<!--БЛОК:имя-->`;
из файла блока берётся только кусок между `<!--БЛОК-НАЧАЛО-->` и `<!--БЛОК-КОНЕЦ-->`.

Семь проверок перед записью:
1. **Теги** — собственный стековый парсер; предварительно `без_кода()` глушит содержимое
   `<script>`, `<style>` и комментариев пробелами (сохраняя длину и номера строк), иначе
   разметка внутри JS-строк считается тегами. Void-элементы и SVG-примитивы игнорируются.
2. **CSS** — баланс `{` и `}` внутри `<style>`.
3. **Палитра** — каждый `var(--c-*)` должен быть объявлен.
4. **Циклы** — запрет `--x: var(--x)` (такая переменная молча становится недействительной).
5. **Структура** — ровно 24 прямых потомка в `.wp`.
6. **JS** — `node -e "new Function(код)"`, синтаксическая проверка скрипта.
7. **Логотип** — запуск `_архив/скрипты/проверка_логотипа.py` (8 правил начертания).

После успеха: копия прежней версии уходит в `_архив/вёрстка/report_prevN.html`,
пишется новый `report.html`, затем запускается `проверка_вёрстки.py` со сверкой с
предыдущей версией (что пропало и какие значения свойств изменились).

**Два дефекта, найденные при запуске:**
* сторож логотипа вызывается **после** `io.open(ИТОГ,'w').write(s)` — обещание «без всех
  проверок файл не перезаписывается» для него не выполняется;
* в `проверка_логотипа.py` зашиты абсолютные пути `/home/user/web/report.html` —
  на любой другой машине скрипт падает с `FileNotFoundError`, и сборка сообщает
  `✗ ЛОГОТИП: Traceback`, уже переписав отчёт.

**И ещё одно.** Сейчас в `каркас.html` **нет ни одной метки** `<!--БЛОК:…-->`: все блоки
возвращены внутрь каркаса, а файлы в `части/` — отдельные копии, в сборке не участвуют.
Значит `собрать.py` фактически копирует каркас в `report.html`. А каркас отстал от отчёта:
в нём «счетикс» без ё, тогда как в `report.html` и в эталоне книги (`09d_Логотип`) —
«счётикс». Пересборка молча откатывает это в 7 местах (проверено запуском).

## 8.2 `блок.py`

```
python3 блок.py список          что есть и что вынесено
python3 блок.py вынести 03      вырезать блок в части/03.html
python3 блок.py вернуть 03      вставить обратно в каркас
python3 блок.py собрать 03      пересобрать обвязку файла блока
```
`карта()` строит соответствие «номер блока, видимый в отчёте → исторический id в вёрстке»
(у блока 03 это `card06`; id менять нельзя — на них завязан CSS). `найти_блок()` находит
границы `<div class="card" id="…">…</div>` с учётом вложенности. `обвязка()` оборачивает
блок в полноценную страницу: реальные стили и скрипт отчёта плюс «щит» — подмена
`document.getElementById`, возвращающая невидимую пустышку для отсутствующих элементов,
иначе `render()` падает на первом же обращении к чужому блоку.

Оговорка из инструкции: в `части/03.html` есть панель просмотра резерва 0/5/10/15 %,
которая стоит **вне** меток и в отчёт не идёт; команда «вынести» пересоздаёт файл и
панель стирает — её нужно вставлять заново.

## 8.3 `превью.py`
`python3 превью.py card01` — собирает одноблочную страницу из каркасных стилей и скрипта,
подменяя `$` на версию с пустышкой, и кладёт `_превью_card01.html` в корень проекта.

## 8.4 `проверка_вёрстки.py`
Пять проверок: баланс скобок и тегов; необъявленные переменные; незакрытые медиазапросы;
дубли селекторов (позднее правило перебивает раннее по тем же свойствам); **сверка с
прежней версией** — что пропало и у каких важных свойств (`margin`, `padding`, `font-size`,
`gap`, `grid-template-columns`, `display`, `background`…) изменились значения. Пятая —
главная: она ловит «правка задела то, чего не просили».

# 12. ДЕФЕКТЫ И РИСКИ

### 🔴 1. `taxOf()` в анкете почти не зависит от выручки
Для `usn15` и `ausn20` база берётся от целевого дохода, поэтому налог — константа:

| Выручка | Налог по `taxOf` (УСН 15 %) | Эффективная ставка |
|---|---|---|
| 300 000 ₽ | 303 348 ₽ | **101 %** |
| 1 000 000 ₽ | 303 348 ₽ | 30 % |
| 2 000 000 ₽ | 303 348 ₽ | 15 % |

Ломает две величины, которые анкета отдаёт наружу: точка безубыточности `Rb`
(подстановка обратно даёт не 0, а −239 520 ₽ для УСН 15 % и −312 748 ₽ для АУСН 20 %)
и `leftC` — доход при текущей ставке. В отчёте это уже исправлено, но значения из анкеты
остаются в JSON и могут быть использованы при любой доработке.
Мелочь того же рода: `Rb` для УСН 6 % не учитывает `CRED` — остаток +3 000 ₽.

### 🔴 2. Две модели вместо одной
См. раздел 10. Нарушено базовое правило проекта «источник правды один».

### 🟠 3. Автоподбор режима сравнивает величины, которые всегда равны
`нетто = R − C − taxAll − aq` по построению равно `Ny` в любом режиме, поэтому строгое `>`
никогда не срабатывает и «лучшим» остаётся первый прошедший по лимиту — `npd`.
Корректный критерий — **минимум требуемой выручки R** (минимальная ставка часа).

### 🟠 4. Нет защиты от отрицательных и взрывных значений
* Продвижение 7,5 ч/день → `pool = −122 ч`, `sh` отрицательный, ставка **−84 055 ₽/ч**.
  Проверка `sh > 0` стоит только на кнопке «Рассчитать», а живой пересчёт уже показывает минусы.
* `D − ставка` нигде не проверяется: эквайринг 30 % + фонд 30 % + резерв 15 % дают D = 0,25
  и выручку 8,7 млн; при больших процентах знаменатель уйдёт в минус и ставка станет отрицательной.
* `S = V('shoot_manual')` без `|| 1` — при пустом поле `pt = cl`, `sh = 0`.

### 🟠 5. Сборка отчёта
Сторож логотипа падает из-за абсолютных путей и вызывается после записи файла (раздел 8.1).

### 🟡 6. Каркас отстал от отчёта
Пересборка откатывает «счётикс» → «счетикс» в 7 местах, вопреки эталону из книги.
Плюс в каркасе нет меток блоков — механизм `блок.py`/`собрать.py` сейчас работает вхолостую.

### 🟡 7. `DEMO` в отчёте устарел
При пустом `localStorage` показывается несуществующий сценарий (доход 108 999 ₽,
Canon по старой цене, выручка 2,14 млн вместо 2,04 млн).

### 🟡 8. Книга не пересчитана
Ни у одной формульной ячейки нет кэшированного значения — самопроверки листа 04
в самой книге никогда не отображались. Блок «Сколько вы теряете» на листе 04 сломан
(съехали ссылки: `B41 = B38 − B37`, строка 43 без формулы).

### 🟡 9. Методические риски (не баги)
* НПД на грани: дефолтный сценарий даёт 2,04 млн — 85 % лимита; при доходе 150 000 ₽/мес
  выручка 2,58 млн уже выбивает из режима.
* Амортизация считается по цене покупки, а заменять технику придётся по будущей цене —
  фонд обновления систематически занижен на инфляцию.
* Упущенная выгода за обучение (4 мес × доход ≈ 441 тыс) амортизируется 7 лет и попадает
  в цену клиента — самая крупная и самая спорная строка расходов (74 409 ₽/год).
* Фонд развития и резерв скидок входят в знаменатель и тем самым уменьшают налоговую базу
  на режимах «Доходы−Расходы», хотя расходами не являются.
* НПД без взносов = без стажа и пенсионных баллов; в сравнении режимов это не отражено,
  хотя разница 57 390 ₽/год именно за это.

### ✔ Что проверено и работает
Главное тождество (на руки = цель) — точно, во всех 7 режимах, с резервами и без.
Три равенства иерархии времени. Сумма сегментов кольца = выручка, сумма доходных = доход.
Инвариант сетки скидок. Налоговые константы 2026 (57 390 ₽, кап 321 818 ₽, порог НДС
20 млн, лимит НПД 2,4 млн, АУСН 60 млн) соответствуют закону.

Проведена машинная сверка всех связок; подробности и рабочие таблицы — в

13 цветов кольца в `CO[]` совпадают с листом `12_Диаграммы` один в один; все цены и

**Что добавилось к списку дефектов:**

1. **Фонд программы лояльности не сходится при длинных съёмках.** При резерве 5 % и
   съёмке 8 часов сумма трёх направлений — 211 052 ₽ против фонда 107 976 ₽, а доля
   заказов от постоянных клиентов достигает 61 % при заявленном потолке 30 %. Причина —
   `Math.max(…, 1)` (минимум один клиент на ступень и один сертификат каждого номинала)
   без проверки остатка бюджета.
2. **`data-t` не связывает книгу и вёрстку.** Атрибут нигде не читается кодом: 69 надписей
   существуют только в HTML, 80 ключей книги не имеют пары в вёрстке, у 20 совпадающих
   ключей тексты разошлись.
3. **Лист `12_Диаграммы`, раздел Д3 (сетка недели) устарел** — в книге зелёная градация,
   в коде разноцветная схема.
4. **21 идентификатор из `08c_Структура_отчёта` в отчёте отсутствует** — лист описывает
   предыдущую редакцию разметки.
5. **9 мёртвых `id`**, среди них `acq_name`: переименование комиссии пользователем никуда
   не передаётся; `ctaLink` — ссылка «30 постов» не проставляется.
6. **275 неиспользуемых CSS-классов** — следы удалённых блоков оплаты и опроса.
7. **`каркас.html` отличается от `report.html` ровно 7 строками** — все про букву «ё» в
   слове «счётикс»; `части/03.html` при этом актуален и совпадает с отчётом байт в байт.
