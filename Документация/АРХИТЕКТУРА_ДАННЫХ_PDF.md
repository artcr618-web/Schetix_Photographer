# Счётикс · архитектура данных PDF

Обновлено: 30 августа 2026 года.

## 1. Главный принцип

PDF не содержит отдельной вручную заполненной копии расчёта. Chromium печатает
`Веб/report.html`, а report получает один объект `d` из настоящего `calc()`.
Поэтому изменение пользовательских значений сначала меняет `calc()`, затем `d`,
затем HTML-отчёт и только после этого PDF.

```text
анкета → calc() → d → report.html → режим печати → PDF
```

Контрольные PDF из папки `PDF/` — только демонстрационные результаты этой
цепочки. Они не являются источником данных.

## 2. Подробная детализация

### 2.1. Вводные данные

Первая таблица детализации не перечисляет поля повторно. Она строится во время
открытия отчёта из двух массивов контракта:

- `d.answers` — активные одиночные ответы анкеты;
- `d.catalog` — активные позиции динамических каталогов.

Это означает:

- новое активное поле, зарегистрированное сборщиком ответов `calc()`, появляется
  в «Вводных данных» report и PDF без отдельной правки PDF;
- новая строка существующего каталога появляется автоматически;
- исключённая ветка не попадает в детализацию, потому что `calc()` не включает
  её в `d.answers` или `d.catalog`;
- сырое значение при этом может сохраняться в анкете, как требуют правила
  эффективных нулей.

Одного появления нового `<input>` в HTML недостаточно. Для поля должны быть
утверждены смысл, единица, номер блока и правило активной ветки. После этого оно
включается в единый сборщик `answers`; отдельного шаблона PDF для него не нужно.
Такое ограничение защищает отчёт от публикации технических переключателей,
скрытых полей и неактивных ответов.

### 2.2. Расчётные таблицы

Таблицы «Время», «Расходы», «Финансовые вложения», «Резервный фонд», сравнение
ставок, износ, прайс и программа лояльности получают числа только из `d`.
Их состав строк и колонок является явной пользовательской схемой в report.

Новый расчётный показатель нельзя безопасно разместить полностью автоматически:
программа не может сама решить, в какой раздел его поставить, какие периоды
показывать и как назвать строку. Поэтому для нового показателя порядок такой:

```text
понятие → формула calc() → поле d → утверждённый раздел детализации → PDF
```

После включения в схему значения во всех экземплярах отчёта и PDF меняются
автоматически вместе с `d`.

## 3. Справочник

Единственный источник пользовательских понятий — лист `01_Глоссарий` основной
книги. В справочник report/PDF публикуются все строки, у которых:

- «Назначение» равно `user`;
- заполнены «Наименование» и «Определение».

Отдельно сохраняется уже утверждённая публикация meta-понятия «Значение по
умолчанию»: оно остаётся в пользовательском справочнике, не меняя назначения в
глоссарии.

Скрипт `Инструменты/справочник_в_отчёт.py` читает книгу и пересобирает массивы
справочника в `Веб/report.html` и `Веб/Части/каркас.html`. Он включён первым
шагом в `Инструменты/карта.py`.

Поэтому после утверждённого добавления нового `user`-понятия достаточно выполнить:

```bash
python3 Инструменты/карта.py
python3 Инструменты/создать_pdf_отчёта.py
```

Новое определение автоматически появится в report и в PDF справочника.
Дубли, пустые user-определения и расхождения блокируют проверку.

## 4. Контрольные сценарии

### Сценарий А · новое определение

1. В `01_Глоссарий` добавляется утверждённая строка `user`.
2. `карта.py` запускает `справочник_в_отчёт.py`.
3. Понятие появляется в массивах `REFD` и `СПР`.
4. PDF справочника получает новую статью при следующей сборке.
5. `сверить_глоссарий.py` подтверждает ноль неопубликованных user-понятий и
   ноль различающихся определений.

### Сценарий Б · новое одиночное поле анкеты

1. Утверждаются название, единица, номер блока, валидация и правило активности.
2. Поле включается в сборщик `answers` внутри `calc()`.
3. Оно появляется в `d.answers` только в активной ветке.
4. Таблица «Вводные данные» добавляет строку автоматически.
5. Headless-сценарии проверяют активную и выключенную ветки.

### Сценарий В · новая позиция каталога

1. Позиция попадает в действующий каталог анкеты.
2. `calc()` включает активную позицию в `d.catalog`.
3. Детализация автоматически добавляет строку с ценой и сроком или периодом.
4. Исключённый каталог не передаёт позицию в report.

### Сценарий Г · новый расчётный показатель

1. Формула создаётся только в `calc()` и зеркалируется на листе `calc`.
2. Результат включается в контракт `d` и лист `Полный_отчёт`.
3. Владелец утверждает раздел, подпись и разрезы строки детализации.
4. После однократного включения строки report и все PDF используют значение
   автоматически.
5. Сценарная сверка Excel и headless-проверка подтверждают связь.
