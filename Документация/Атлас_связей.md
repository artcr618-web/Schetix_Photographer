1. `09_Тексты` → найти по ключу → колонка «Текст».

Проверить: «все CSS-переменные объявлены» + глазами кольцо и сетку.

### 1.4 Добавить или изменить позицию расходов
1. `03_Каталоги` → строка с кодом формы.
2. `CAT.FormXXX.rows` в `calc.html` — **название должно совпадать буквально**

3. Если появилась новая форма — завести таблицу `t_FormXXX` в разметке, чекбокс
   `data-exc`, ветку в `sumF()`, слагаемое в `amort`/`vari` внутри `calc()`, поле в

Проверить: «сумма 13 сегментов = выручка» — она поймает потерянный расход.

### 1.5 Поменять блок отчёта
```
cd web
python3 блок.py вынести 03      # блок 03 = card06 (историческое имя, менять нельзя)
# правим вынесенный блок (python3 блок.py вынести NN) ТОЛЬКО между <!--БЛОК-НАЧАЛО--> и <!--БЛОК-КОНЕЦ-->
python3 собрать.py              # пересобрать и прогнать 7 проверок

```
**Осторожно, две ловушки:**
* сейчас в `каркас.html` вообще нет меток `<!--БЛОК:…-->`, а сам каркас отстал от отчёта
  на 7 строк (в нём «счетикс» без ё). Первая же пересборка откатит букву ё. Перед началом
  работы с блоками каркас надо синхронизировать;
* «вынести 03» пересоздаёт файл и стирает панель просмотра резерва 0/5/10/15 % — её надо
  вставлять заново, иначе вариант с программой лояльности не посмотреть.

### 1.6 Добавить блок в отчёт
`собрать.py` жёстко ждёт **24 прямых потомка** `.wp` — надо поднять `ожидать_блоков`
в `проверить(s, ожидать_блоков=24)`, иначе сборка встанет. Плюс: id вида `cardNN`
использует `блок.py` для поиска границ — новый блок должен следовать тому же шаблону
`<div class="card" id="cardNN"><div class="bn">NN<…`.

### 1.7 Поменять формулу расчёта
Единственное место — `function calc()` в `calc.html` (плюс зеркало в книге на листе
`05_Расчёт`). Но помните: **налоги в отчёте считаются отдельно** (`налог0`, `netUSNDR`
и т. д.) — правка только в анкете разъедет цифры. До объединения моделей правки нужно
дублировать в оба файла.
Проверить: `проверить.py` — семь строк «на руки = цель» и три строки иерархии.

## 3. СПРАВОЧНИК СВЯЗЕЙ

### 3.1 Поле анкеты → переменная `calc()` → что зависит
```
income_month   → Ny, eduOpp(упущенная выгода) ⇒ ВСЯ модель + амортизация обучения
current_rate   → cur, Rc, leftC              ⇒ блоки 05 «сценарии» и 06 «больше заказов»
shoot_manual S → pt, py, sh, post, clT ⇒ ставка, сетка скидок, средний чек лояльности
post_ratio K   → pt (через M=1+K)            ⇒ то же + сетка недели
client_time cl → pt, clT                     ⇒ то же + доля накладных в скидке
promo_per_day  → promo → side → gross → pool ⇒ количество проектов и ставка
acc_per_quarter→ accT → side                 ⇒ то же (только если «веду сам»)
acc_cost_month → accM → vari                 ⇒ расходы (только если «нанимаю»)
fm_on/fm_pct   → fmT → pool                  ⇒ проектные часы; сегмент «Форс-мажоры и простой»
ws_mode + home_rent/home_util/home_area/cab_area/office_* → wsY → vari, varRent
edu_life + таблица Form006 → eduOpp, eduY → amort, depEdu
site_mode + site_cost/site_life → siteY → amort, depSite
site_mode(сам) + site_hours/site_life → sdiv → D (знаменатель!)
acq_rate, acq_share, доп. комиссии → a → D и aq
fund_on/fund_pct → fundP → D, fundY          ⇒ сегмент 12 кольца
disc_on/disc_pct → discP → D, discY          ⇒ сегмент 13 + ВЕСЬ блок программы лояльности
regime + npd_who → rg → RT → R и taxAll      ⇒ ставка, блок 04
tax_off        → RT=0                        ⇒ все налоги обнуляются
```

## 4. ОПАСНЫЕ МЕСТА (где легко сломать)

1. **Имена CSS-классов.** В `09b` зафиксирован реальный случай: класс `.cn` уже был занят
   информационными плашками (`min-height:210px` + декоративный круг), из-за чего шапка
   таблицы блока 07 стала 210 px. Перед добавлением класса — `grep` по каркасу.
   Особенно опасны короткие имена: `.cn`, `.cp`, `.ch`, `.dn`, `.ds`, `.lg`.
2. **`id` карточек `cardNN`.** На них завязан `блок.py` (поиск границ блока) и CSS.
   Номер в отчёте и `id` в вёрстке **не совпадают** (блок 03 = `card06`) — это исторически,
   менять нельзя.
3. **Порядок сегментов кольца.** `CO[]`, `LB[]`, `REFLB[]` и `parts()` должны совпадать
   по длине и порядку (13 элементов). Сдвиг на один — и легенда покажет чужие подписи.
4. **`.wp` = ровно 24 ребёнка.** Любой новый `<div>` на верхнем уровне остановит сборку.
5. **JS в одном IIFE.** Ошибка в любом месте гасит **весь** скрипт: отчёт останется
   с пустыми цифрами. Поэтому проверка `node -e new Function(...)` в `собрать.py` обязательна.
6. **Кириллица в base64.** Запасной канал передачи данных работает через связку
   `unescape(encodeURIComponent())` → `btoa` → `encodeURIComponent`, а на приёме — зеркально.
   Ломается от любого «упрощения».
7. **Сторож логотипа** запускается после записи файла и содержит абсолютные пути —
   он не защищает, а только сообщает. До починки считайте, что проверка знака ручная.

## 5. ЧТО НАШЛОСЬ В ЭТОЙ ИТЕРАЦИИ (сверх прежнего аудита)

1. **Фонд программы лояльности не сходится на длинных съёмках.** Книга (`13b`) обещает
   «сумма трёх направлений = бюджет фонда». Фактически:
   | Сценарий | Фонд | Постоянным | Сертификаты | Объём | Сумма |
   |---|---|---|---|---|---|
   | резерв 15 % | 365 833 | 47 234 | 108 500 | 210 099 | 365 833 ✓ |
   | резерв 5 % | 107 976 | 41 800 | 33 000 | 33 176 | 107 976 ✓ |
   | резерв 5 %, съёмка 6 ч | 107 976 | 78 712 | 86 500 | 0 | **165 212 ✗** |
   | резерв 5 %, съёмка 8 ч | 107 976 | 111 552 | 99 500 | 0 | **211 052 ✗** |
   Причина — `Math.max(…, 1)`: минимум один клиент на каждую ступень и минимум один
   сертификат каждого номинала, независимо от бюджета. Заодно ломается второй
   ограничитель: доля заказов от постоянных доходит до **61 %** при заявленном
   потолке 30 %. Сценарий реальный: свадебный фотограф со съёмками 6–8 часов.
2. **`data-t` — мёртвый маркер.** Реестр текстов и вёрстка живут независимо: 69 надписей
   вне книги, 80 книжных ключей без вёрстки, 20 расхождений в тексте.
3. **Сетка недели в книге не соответствует коду.** `12_Диаграммы` Д3 описывает зелёную
   градацию (`#1B9331`, `#35B94C`, `#6FD183`, `#A6E5B2`, `#CDF2D5`), а в коде разноцветная
   схема: обработка `#A9DDB8`, клиент `#F5B301`, продвижение `#EC4899`, учёт `#EF4444`.
4. **21 `id` из `08c_Структура_отчёта` не существует** в текущем отчёте (`bRate`, `bProj`,
   `condGrid`, `cstA…cstD`, `finRate`, `drows`, `txrule`, `pmkText` и удалённые блоки).
5. **9 мёртвых `id`**, из них содержательный — `acq_name`: пользователь может переименовать
   комиссию, но это никуда не идёт.
6. **275 неиспользуемых CSS-классов** в двух файлах — следы удалённых блоков оплаты и опроса.
7. **`каркас.html` совпадает с `report.html` с точностью до 7 строк** — все про букву ё.
   Вынесенные блоки сверяются с отчётом байт в байт (собрать.py).

## 6. РЕГЛАМЕНТ БЕЗОПАСНОЙ ПРАВКИ

```
1. python3 Инструменты/проверить.py        # снимок «до»: 42 ✓ / 14 ✗ / 5 !
2. правим одно место
3. python3 Инструменты/проверить.py        # число ✓ не должно уменьшиться,
                                           # число ✗ не должно вырасти
4. если трогали отчёт:  cd web && python3 собрать.py
5. если трогали книгу:  python3 Инструменты/карта.py   # пересобрать индексы
6. глазами: index.html → calc.html → report.html на живом сервере
```
Любая правка, после которой падает ранее зелёная проверка, — регресс. Именно поэтому
14 текущих падений полезно оставить как есть: они фиксируют известные дефекты, и когда
мы будем их чинить, тест позеленеет и подтвердит, что починка настоящая.
