# Счётикс — алгоритм взаимодействия и текущая стадия

Обновлено: 28 августа 2026.

## 1. Роли

### Владелец

Владелец определяет:

- смысл понятий;
- пользовательские названия и определения;
- состав показателей;
- методику расчёта;
- пользовательскую подачу и дизайн;
- приоритет работ.

Голосовые формулировки могут содержать оговорки. Ассистент понимает намерение,
но не принимает продуктовые решения вместо владельца.

### Ассистент

Ассистент:

- устанавливает фактические связи до правки;
- находит источник, а не первое текстовое совпадение;
- прослеживает последствия на несколько шагов;
- меняет только утверждённое;
- синхронизирует все обязательные поверхности;
- запускает проверки после каждой правки;
- фиксирует находки и следующую задачу.

Название продукта пишется **Счётикс**, с прописной и через «ё».

## 2. Как выполняется одна задача

1. Установить, что меняется: буква, понятие, формула, состояние или дизайн.
2. Найти источник правды.
3. Построить цепочку влияния.
4. Остановиться, если требуется смысловое решение владельца.
5. Зафиксировать состояние до правки.
6. Изменить минимально необходимое.
7. Провести изменение через зеркала.
8. Пересобрать автоматические листы и книгу, если требуется.
9. Запустить полную проверку.
10. Сообщить, что сделано и что сознательно не изменялось.
11. Обязательно назвать следующую задачу и её место в дорожной карте.

Нельзя завершать действие сообщением «сделано» без направления дальше. Если
нужно решение — показывается один конкретный вопрос. Если решение не нужно —
ассистент продолжает техническую работу самостоятельно.

## 3. Источники правды

| Сущность | Источник |
|---|---|
| Исполняемый расчёт | `calc()` в `Веб/calc.html` |
| Понятия и определения | `01_Глоссарий` основной книги |
| Пользовательский справочник | `СПРАВОЧНИК` в `Инструменты/таблицы_прототип.py` |
| Формулы книги | `calc` |
| Состав групп | `Состав` |
| Значения и состояния анкеты | `Значения_по_умолчанию` |
| Страницы, блоки, элементы и ветки | `Интерфейс` |
| Пользовательские показатели и контракт `d` | `Полный_отчёт` |
| Программа лояльности | `Программа_лояльности` и фактический код report |
| Правила | `Архитектура — Правила модели и интерфейса.md` |
| Задачи | `Задачи/З-*.md` и `Задачи/РЕЕСТР.md` |

Определения глоссария предназначены пользователю. Формулы, ID, внутренние ветки
и порядок промежуточных действий хранятся в `calc` и паспортах.

## 4. Обязательная цепочка влияния

```text
понятие
→ поле анкеты
→ calc()
→ поле d
→ report
→ основная книга
→ паспорт
→ правило
→ тест
```

Для новой вёрстки используются:

- `data-page-id`;
- `data-block-id`;
- `data-branch-id`;
- DOM-ID;
- `data-t`;
- поля `d`;
- понятия глоссария;
- паспорта;
- `Интерфейс`.

Новая вёрстка меняет расположение и оформление, но не создаёт вторую логику.

## 5. Правила, которые нельзя нарушать

1. Не переименовывать понятие и не менять состав без решения владельца.
2. Любое пользовательское название сверять с `01_Глоссарий`.
3. Все понятия с назначением `user` дословно публиковать в справочнике.
4. Не добавлять в пользовательское определение формулы и внутренние ID.
5. Не улучшать соседний элемент по пути.
6. Не делать самостоятельный редизайн report до получения новой вёрстки.
7. Смысловые и расчётные изменения проводить через действующий HTML сразу.
8. Выключенный необязательный параметр остаётся в структуре и получает
   эффективный ноль.
9. Отрицательный пользовательский ввод отклоняется; вычисленный убыток
   сохраняется со знаком минус.
10. Деньги внутри модели хранятся точно; пользователю показываются до рубля.
11. Практическая ставка округляется вверх до 100 ₽ только в утверждённых местах.
12. Логистика не входит в базовый расчёт и учитывается для конкретного проекта.
13. Старая архивная книга и архивные документы не являются рабочими источниками.
14. После правки запускать `проверить.py`; значение «упало» всегда 0.
15. Найденная, но не исправленная проблема немедленно попадает в дорожную карту
    или отдельную задачу.

## 9. Следующий крупный этап

Пройти поля анкеты по одному: обязательность, ноль, минимум, максимум, шаг,
межполевые ограничения и понятные ошибки без скрытой подмены.

Порядок сведения:

1. сохранить утверждённую расчётную логику;
2. сопоставить страницы и блоки по стабильным ID;
3. сопоставить поля с контрактом `d`;
4. перенести пользовательские тексты;
5. обновить `Интерфейс`;
6. добавить report-тексты в `Тексты`;
7. добавить report-CSS в `CSS_и_компоненты`;
8. проверить мобильную и печатную версии;
9. выполнить публикационную проверку.

Параллельно не теряются отдельные задачи:

- З-035 — валидация полей;
- З-039 — публикационная копия без DEMO;
- З-042 — экономика постоянного клиента;
- З-043 — аналитика, UTM и цели;
- З-012/013/014 — домен, платежи и счётчик.
