# 1. ЧТО ЭТО ЗА ПРОДУКТ

## Задача

Счётикс — калькулятор юнит-экономики съёмочного часа для фотографа. Он решает
**обратную задачу ценообразования**. Обычный калькулятор отвечает «сколько я
заработаю при ставке X». Счётикс идёт наоборот:

```text
Желаемый доход → сколько нужно Выручки → сколько стоит съёмочный час
```

Расчёт целиком выполняется в браузере. Бэкенда нет, база данных не нужна,
данные пользователя никуда не отправляются.

## Главное сообщение продукта

Из 1533 эффективных рабочих часов в году фотограф продаёт клиенту только
**216,6 часа — это 14 %**. Каждый оплаченный час съёмки тянет за собой три часа
обработки и час работы с клиентом, плюс поиск заказов и отчётность, которые
не оплачиваются вообще. Вся модель существует, чтобы показать это одно число
и вывести из него честную ставку.

Отсюда разрыв, который видит пользователь:

| Ставка часа съёмки | Доход в час на руки |
|---|---|
| 9 430 ₽/ч | 692 ₽/ч |

## Что именно стережёт `проверить.py`

245 проверок в девяти группах. Полный перечень того, что нельзя нарушить:

**1. Модель (~30 проверок).** Для семи налоговых режимов: `R − C − aq −
taxAll − fundY − discY = Ny`. Иерархия времени: `promo + accT + fmT + pool =
NT` и `sh + post + clT = pool`. Сумма 14 секторов кольца равна `R`. Инвариант
сетки скидок: выручка одинакова при любой длительности съёмки, а ставка
убывает. Загрузка: `loadGoal.shoots = py`, `loadGoal.hours = NT`.

**2. Краевые случаи (~15).** Продвижение 7,5 ч/день не даёт отрицательных
часов. Экстремальные проценты не дают `R > 5 млн`. Нулевая длительность
съёмки обрабатывается. Безубыточность сходится в ноль во всех семи режимах и
в четырёх особых ветках.

**3. Идеальный и текущий сценарии (~20).** Шесть веток идеального, восемь
текущего. Убыток не обрезается: `currentLoss = min(результат, 0)`.

**4. Эффективные нули (~40).** Для каждого блока: исключённый блок не
передаёт ни ответов, ни позиций каталога. УСН не передаёт тип заказчиков НПД.
Выключенные фонды не передают ответы, включённые передают даже 0 %.

**5. Пределы полей (~35).** Для каждого поля проверяются `min`, `max`,
`step`, флаги `data-integer` / `data-limit-live` / `data-step-live` **и точный
текст сообщения об ошибке**. Изменить предел, не изменив текст, — падение.

**6. Согласованность файлов (~40).** `report == каркас` побайтно. Названия
ставок только по глоссарию, старые ярлыки запрещены. Десятки проверок на
точные подстроки кода вида `'var rateGoalПередан=Number(d.rateHour)'`.

**7. Структура HTML/JS (~15).** Баланс тегов, ровно 20 прямых потомков `.wp`,
порядок блоков отчёта, пользовательские номера 01–08, 8 правил логотипа,
компиляция JS всех трёх файлов.

**8. Книга ↔ код (~30).** Значения по умолчанию, положения переключателей,
налоговые константы, 19 последовательных `RULE`, существование документов по
ссылкам, 11 meta-понятий дословно, полнота контракта `d`, суммы трёх диаграмм.

**9. Внешние прогоны (~5).** Headless report — 8 сценариев, ZIP передачи,
наличие 9 файлов переезда.

## Шаг 1. Время (строки 3234–3255)

```javascript
promo = EXC['FormPromoTime'] ? 0 : promo_per_day × ND        // 2×219 = 438 ч
accT  = (self && !accEx) ? acc_per_quarter × Q : 0           // 3×4   = 12 ч
idle  = ND × (8 − EFF)                                        // 219 ч — паузы

```

**Защита от абсурда.** Если непроданное время съедает весь год, ставка
становится отрицательной. Введён предел:

```javascript
ПРЕДЕЛ_СТОРОННЕГО = NT × 0.8 = 1226,4 ч
if (side > ПРЕДЕЛ) { пропорционально ужать promo и accT }
```

Далее:

```javascript
gross = NT − side = 1083 ч
fmT   = fm_on ? gross × fm_pct : 0          // резерв на простой, по умолчанию 0
pool  = gross − fmT = 1083 ч                // Проектное время
```

## Шаг 2. Проект (строки 3251–3255)

Ключевое место всей модели:

```javascript
K  = post_ratio = 3          // часов обработки на 1 час съёмки
cl = client_time = 1         // работа с клиентом на проект
S  = shoot_manual = 1        // минимальный заказ
M  = 1 + K = 4

pt = S×M + cl = 1×4 + 1 = 5 ч     // ОДИН ПРОЕКТ ЦЕЛИКОМ
py = pool / pt = 1083/5 = 216,6   // проектов в год
sh = py × S = 216,6 ч             // ОПЛАЧИВАЕМЫХ часов
post = sh × K = 649,8 ч
clT  = py × cl = 216,6 ч
```

Итог: `216,6 / 1533 = 14,1 %` рабочего времени продаётся.

## Шаг 3. Деньги — расходы (строки 3256–3287)

**Рабочее место** — две взаимоисключающие ветки:

```javascript
wsShare = home_area>0 ? cab_area/home_area : 0        // защита от /0 → 0,12
homeHousing = CHK('own_home') ? 0 : home_rent          // RULE-010
wsY = wsEx ? 0
    : (дома ? (homeHousing + home_util) × wsShare × 12
            : (office_rent + office_util) × 12)
// по умолчанию: (40000+7000) × 0,12 × 12 = 67 680 ₽/год
```

**Обучение** — единственное место, где считается упущенная выгода:

```javascript
eduOpp = eduMon × income_month        // 4 мес × 110 216 = 440 864 ₽
eduY   = (eduSum + eduOpp) / eduL     // (80 000 + 440 864)/7 = 74 409,14 ₽/год
```

Курс за 80 000 ₽ реально стоит 520 864 ₽, потому что 4 месяца учёбы — это
4 месяца без дохода.

**Сайт** — две ветки: заказан (`siteY = site_cost/site_life = 10 000 ₽/год`)
или сделан сам (`siteY = 0`, но появляется доля выручки
`sdiv = site_hours/(site_life×NT)` — компенсация Инвестиционного времени).

**Итог расходов:**

```javascript
equip = Form001 + Form002 + Form004
amort = equip + Form013 + eduY + siteY        = 278 687,78 ₽/год
vari  = Form003 + Form010 + Form007 + accM + wsY = 283 980,00 ₽/год
```

Позиции типа `life` делятся на срок службы (камера 166 999/3 = 55 666 ₽/год),

## Шаг 4. Проценты от выручки (строки 3288–3310)

```javascript
a      = эквайринг + доп. комиссии,  зажат в [0; 0,10]
fundP  = фонд развития,              зажат в [0; 0,20]
discP  = запас на скидку,            зажат в [0; 0,15]
sdiv   = компенсация своего сайта
D = 1 − a − sdiv − fundP − discP
if (D < 0.40) D = 0.40      // суммарные отчисления не больше 60 %
```

Без этих рамок ручная подстановка 30 %+30 %+15 % роняла знаменатель до 0,25
и выручка взлетала до 9,4 млн — бессмысленное число.

## Шаг 5. Налоги — функция `taxOf(Rx)` (строки 3311–3341)

Семь режимов. НПД раскрывается по типу заказчика: физлица → 4 %,

## Три ставки — различать обязательно

Родовое понятие «**Ставка часа съёмки (стоимость часа съёмки)**» не имеет ID.
Под ним:

| Понятие | ID | Смысл |
|---|---|---|
| Текущая ставка | `current_rate` | по которой работает сейчас |
| Желаемая ставка | `rateHour` | даёт Желаемый доход |
| Ставка в ноль | `rateZero` | точка безубыточности |

Отдельно: «**Базовая ставка**» (`base_rate`, 1 332 ₽/ч) — час работы **вне
съёмочной площадки**: ретушь, консультации. Без повышающего коэффициента.

«**Доход в час на руки**» (692 ₽/ч) — сравнение с наймом: доход за 11 месяцев
÷ (219 дней × 8 ч). Одиннадцать, а не двенадцать, потому что отпуск уже
заложен в каждую ставку и является дополнительной оплатой, а не зарплатой.

## Выручка и её состав

**Выручка** — всё, что приходит от клиентов. Состав по листу `Состав`:
Желаемый доход + Финансовые расходы + Налоги + Эквайринг + Инвестиционное
время + Резерв на развитие + Резерв на программу лояльности. Резерв на отпуск
отдельно не прибавляется — он **внутри** Желаемого дохода.

**Финансовые расходы (C)** = Финансовые вложения (инвестиции) + Регулярные
расходы специалиста.

**Всего расходов** = `C` + Налоги + Эквайринг. Резервный фонд сюда не входит.

**Резервный фонд** = Резерв на отпуск + на развитие + на лояльность.

## Время

**Рабочее время** 1752 ч (219 × 8) — норма ТК. **Эффективное рабочее время**
1533 ч (219 × 7) — за вычетом перерывов. **Неэффективное** 219 ч.
**Операционное время** — продвижение, поиск заказов, учёт. **Проектное
время** 1083 ч. **Съёмочное** 216,6 ч.

**Инвестиционное время** — обучение и самостоятельный сайт. Не входит в
`workHours`, компенсируется деньгами. Единой суммы в часах не имеет: обучение
в месяцах, сайт в часах — складывать нельзя.

## Эффективное значение — центральное правило

> Каждый параметр всегда существует в структуре. Выключенный, исключённый или
> относящийся к неактивной ветке получает **эффективное значение 0**.

Сырое значение сохраняется для повторного включения. Формулы складывают один
набор эффективных значений — отдельной математики на каждое сочетание
галочек не существует.

Исключение: **обязательный делитель** не обнуляется молча. Расчёт
останавливается с сообщением (RULE-008).

# 10. ГЛАВНОЕ ОДНОЙ СТРАНИЦЕЙ

**Что считает.** Обратную задачу: от желаемого дохода к ставке съёмочного часа.

**Где живёт истина.** `calc()` в `Веб/calc.html`, строки 3233–3586. Всё
остальное — зеркала: книга проверяет, report показывает, PDF печатает,
`price.html` использует. Никто, кроме `calc()`, не считает.

**Три числа, которые всё объясняют:**

```text
1533 ч   эффективное рабочее время в году
 216,6 ч оплачивается клиентом — это 14 %
9430 ₽/ч ставка, при которой фотограф получит 692 ₽/ч на руки
```

**Почему модель заслуживает доверия:**

1. Обратная задача решена численно (90 итераций деления пополам), а не
   подогнана формулой.
2. Налоговые изломы обработаны честно, УСН-15 считается 12 проходами.
3. Упущенная выгода от обучения учтена — редкость для калькуляторов.
4. Каждая ставка берёт налоги от своей базы, себестоимость не завышена.
5. Защиты стоят на всех делениях: ни одного `NaN` под обстрелом
   19 прогонов, включая экстремальные.
6. Убыток сохраняется со знаком минус, а не прячется в ноль.

**Дизайн-система едина.** 90 токенов в 8 семействах, одна гарнитура,
радиусы 12/14 px, тени трёх уровней, шаг сетки 2 px. У 81 общего токена
значения `calc` и `report` совпадают; 14 объявлены только на одной странице.

**Структура жёсткая.** 2 / 39 / 20 блоков зашиты в проверки. Идентификаторы
связаны шаблоном `c_FormNNN` ↔ `t_FormNNN` ↔ `data-add` ↔ `data-exc`;
переименование ломает скрипт и сторожа одновременно.

**Что требует решения владельца** (по убыванию значимости):

1. Демо-набор `price.html` устарел и не покрыт ни одной проверкой —
   открытая без данных страница показывает неверные числа.
2. Строка «Страховые взносы = 0» в отчёте неверна для УСН и АУСН —
   вопрос открыт с 19.08.2026.
3. Молчаливое зажатие поля «Поиск заказов» с 6 ч/день против принципа З-035.
4. Два примечания книги (`calc!H64`, `H65`) противоречат коду по `own_home`.
5. Две записи глоссария без «Назначения» не попадают в справочник, при том
   что «Убыток» показывается в интерфейсе.
6. 41 объявленный, но ни разу не вызванный CSS-токен; статус «используется»
   в книге проставляется жёстко и ничего не проверяет.
7. `price.html` и `index.html` не зарегистрированы в листах `Интерфейс`,
   `Тексты` и `CSS_и_компоненты`.
